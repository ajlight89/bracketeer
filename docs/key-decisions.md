# Key Decisions

This document records the main decisions behind Bracketeer and why they were made, plus every change to the project's scope. Each entry says what was decided, what else was considered, and why. When a decision changes, the entry is updated and the change is noted, so the reasoning stays visible.

## Decisions

| #   | Date       | Decision                                                                                                 | Alternatives considered                    | Why                                                                                                                                                                                                                                        |
| --- | ---------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | 2026-11-09 | Requirements are written as user stories, domain rules, and NFRs, each with an ID that tests cite        | Stories only                               | Each rule is stated once, so a change happens in one place, and every requirement can be traced to the tests that check it.                                                                                                                |
| 2   | 2026-11-09 | Python 3.12 with Tkinter and plain ttk widgets                                                           | A web app; a third-party GUI framework     | Tkinter comes with Python, so there is nothing extra to install or license. ttk widgets look native on Windows without a theme package.                                                                                                    |
| 3   | 2026-11-09 | A layered design with a domain layer that does no input or output                                        | Putting the rules in the window code       | The rules can be tested without a window or files, and the window or the save format can change without touching them (see [design.md](design.md#layers)).                                                                                 |
| 4   | 2026-11-09 | Strategy pattern for tournament formats; formats return round plans and `Tournament` numbers the matches | One class with `if format == ...` branches | A new format is a new class, with no changes to existing code. Numbering matches in one place keeps IDs unique.                                                                                                                            |
| 5   | 2026-11-09 | Save each tournament as one JSON file, behind a `TournamentRepository`                                   | A SQLite database                          | A tournament is small and is always loaded and saved whole, so one file per tournament is simpler: it can be named, copied, and backed up like any document, and it needs no database schema. The Repository keeps the choice replaceable. |
| 6   | 2026-11-09 | The organizer saves explicitly (Save, Save As) and is asked before unsaved changes are discarded         | Saving after every change                  | It matches how people expect documents to work, and it fits the one-file-per-tournament design.                                                                                                                                            |
| 7   | 2026-11-09 | A bye gives no match points; in round robin every player gets exactly one bye when the count is odd      | A bye counts as a win                      | In round robin, giving every player one bye means byes can't change the final order, so awarding points for them adds nothing.                                                                                                             |
| 8   | 2026-11-09 | Round robin tiebreakers: match points, then game differential, then original seed                        | Adding head-to-head                        | Game differential is simple to explain and to test. Seed last guarantees one complete, repeatable order.                                                                                                                                   |
| 9   | 2026-11-09 | A player who leaves mid-tournament is handled by recording forfeits                                      | An automatic "withdraw player" feature     | Forfeits already cover the case with no extra rules (see the scope changes below).                                                                                                                                                         |
| 10  | 2026-11-09 | Ship a single-file `.exe`, built locally with PyInstaller and attached to the GitHub release             | Building the `.exe` in GitHub Actions      | Organizers don't need Python (US-12). Building locally keeps the setup simple; GitHub Actions still runs the linter and the tests on every pull request.                                                                                   |

## Scope changes

The scope was set with MoSCoW priorities (see [user-stories.md](requirements/user-stories.md#story-index)). These are the features that were considered and deliberately left out of v1.0, or moved to a lower priority, and why.

| Date       | Change                                                       | Why                                                                                                                                                        |
| ---------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 2026-11-09 | Swiss tournaments (US-06): Won't                             | Swiss pairing is the most complex format by far. Round robin and single elimination cover the common small-event cases.                                    |
| 2026-11-09 | Withdrawing a player (US-13): Won't                          | Recording forfeits covers it (decision 9).                                                                                                                 |
| 2026-11-09 | CSV import (US-14): Won't                                    | Fields are small (at most 64 players), so typing names is manageable.                                                                                      |
| 2026-11-09 | Double elimination (US-15): Won't                            | It needs a second bracket and a grand final. The Strategy design leaves room to add it later as one new class.                                             |
| 2026-11-09 | Publishing to GitHub Pages (US-16): Won't                    | It depends on web export, and Bracketeer makes no network connections (NFR-SE-3). An exported file can still be shared like any other file.                |
| 2026-11-09 | Undo and redo (US-08): Could                                 | Clearing and re-entering a result fixes a mistake, so undo is a convenience rather than a necessity.                                                       |
| 2026-11-09 | Web export (US-11): Could                                    | The standings are visible in the app itself; sharing a page is a nice extra.                                                                               |
| 2026-11-09 | AI-assisted seeding: written as a requirements proposal only | It needs match history across many tournaments, which v1.0 can't collect yet. See [ai-smart-seeding.md](requirements/ai-smart-seeding.md).                 |
| 2026-11-09 | Testing focuses on unit tests and property-based tests       | Mutation testing, coverage targets, and automated security scanning were considered and left out to keep the time on the application and its requirements. |
